# Adding sensors and observations

Check the current code before following these steps; names and details may have changed.

## A new observation from an existing sensor

Use this when the node already subscribes to the message holding the data, for example another
field of an existing message:

1. If the sensor's callback does not keep that field in the value it stores, extend the callback
   to keep it (following the callback rules under "A new sensor").
2. If the value is not yet passed on, unpack it into a variable in the node's policy calculation
   function and describe it in `EXPLANATION OF THE OBSERVATIONS`.
3. Add a parameter for it to `convert_observations` in `policy/input_output.py`, with a docstring.
4. Represent it with a type in `policy/input_output.py` (see "Observation types" below) and add it
   to `CarObservations` or `ObservedCarState`.

If the logged `CarObservations` or `CarActions` shape changes, review
`2.03_adding_and_using_test_data` and update the matching schema.

## A new sensor

Adding a sensor means editing `scripts/policy_node.py`, so only do it when the task intends it.
The node only subscribes to sensor topics, so a DREAM component must already publish the sensor's
topic; DREAM owns the hardware components.

In the node:

1. Add the sensor's name to the list of sensor names. That name is also used for its timeout
   parameter, `required_sensors` and freshness checks.
2. If its message has no header, exclude it from the stamped sensors, and store it without a stamp.
3. Subscribe to its topic with a suitable QoS profile.
4. In its callback, validate the whole message before storing it, and store it with the node's
   store helper. Invalid data must never be stored, because storing it refreshes its freshness.
   Keep meaningful special values (such as infinity) rather than replacing them with zeros.
5. Never block in the callback, for example by waiting for a TF transform.
6. Only one selected update mode triggers policy steps, so the new callback should only store its
   data. Do not make the new sensor a second, simultaneous trigger.
7. The node passes the stored value, age and stamp to the policy calculation function under the
   sensor's name. Unpack it there and describe it in `EXPLANATION OF THE OBSERVATIONS`, then pass
   it to `convert_observations`.

Elsewhere:

- `config/ai4r_policy.yaml`: add its `sensor_timeout_s` entry and list it among the valid
  `required_sensors` names. The node declares the timeout parameter automatically from the sensor
  name, so it does not need the steps in `2.02_adding_parameters`.
- `package.xml`: add an `exec_depend` if its message type comes from a new package.
- `README.md`: add its topic to the interfaces table.

Then follow "A new observation from an existing sensor" for the policy side.

## Observation types

- Use a frozen dataclass, or a float subclass for a single value (as for wheel speed).
- Include a `sensor_age: SensorAge` so the policy can see how old the sample is.
- Give the type and every attribute a docstring stating its frame, units and meaning, including
  everything from the node's explanation comments (e.g. in the `EXPLANATION OF THE OBSERVATIONS` block).
- Do not reword or rewrite `EXPLANATION OF THE OBSERVATIONS` just to match policy-package
  docstrings; treat that block as the more definitive version. Describing a newly added sensor or
  observation there remains expected when following the steps above.
- Make the type JSON-serialisable for data logging: subclass `Serialisable` from
  `policy/serialisation.py` when the default field-based methods work, otherwise implement
  `serialise()` and `deserialise()` (as for cone batches and float subclasses).
- A missing or expired optional observation is `None` in `CarObservations`, never a zero value.
