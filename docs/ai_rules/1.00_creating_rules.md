# Creating rules

Use this rule when creating, changing, renaming or removing a rule in `docs/ai_rules/`.

## File name and number

- Each rule is one Markdown file in `docs/ai_rules/`, named `X.XX_rule_name.md`.
- `X` is the category and `XX` is the rule's two-digit number within that category:
  - `0.XX`: root rules that must be read for every major request.
  - `1.XX`: rules about modifying the documentation and `ai_rules`.
  - `2.XX`: coding rules that must be followed when changing the source code.
  - `3.XX`: process guides and other general documentation to enhance understanding.
- `X.00` is the main rule of its category. Give a new rule the next free number in its category.
- `rule_name` is lower-case snake_case and describes the topic, for example `codebase_structure`.
- Do not renumber or rename existing rules unless asked, because other rules refer to them by name.

## Header

The first four lines of every rule are exactly:

```text
name: X.XX_rule_name
description: Short phrase naming the rule's topic.
when_to_use: always
-----
```

- `name` is the file name without `.md`.
- `description` is a single, concise line, because the index is read for every major request.
  Name the topic directly, without filler such as "Explains" or "This rule", while still letting a
  reader decide from it alone whether the rule applies to their task.
- `when_to_use` is exactly `always` or `when_applicable`:
  - `always`: the rule is needed for nearly every request. Keep these few, because every one is
    read every time.
  - `when_applicable`: the rule is only needed for some tasks, chosen using its description.
- The fourth line is exactly five hyphens (`-----`). The rule's content starts on the next line.

## Index entry

Every rule has one entry in `docs/ai_rules/rule_index.json`, a JSON array ordered by rule number:

```json
[
    {
        "name": "X.XX_rule_name",
        "description": "Short phrase naming the rule's topic.",
        "when_to_use": "always"
    }
]
```

- `name`, `description` and `when_to_use` must match the rule's header exactly.
- Keep index descriptions concise: every word is read for every major request.
- Keep the file valid JSON: double quotes, and commas between entries but not after the last one.

## Rule content

- Cover one topic per rule. Split a rule that covers unrelated topics.
- Be concise. Use short headings, lists and imperative sentences.
- Describe the required behaviour, not an inventory of every file or example. Stable paths or
  symbols are fine when they anchor that behaviour; avoid lists that go stale when the tree
  shifts. Prefer general guidance; point to the code or documentation instead of copying details
  such as line numbers or full function signatures.
- Use Australian or British English spelling.
- Refer to other rules by name, for example `0.00_root_rule`.

## Accuracy

Rules are followed without being re-checked, so an inaccurate rule causes repeated mistakes and
conflicts with other rules.

- Check every statement against the code or documentation before adding it.
- Only include steps or requirements that are documented or requested. Do not add conventions that
  are only inferred; if one is useful, suggest it to the user instead.
- Read the related rules, `AGENTS.md` and the repository documentation, and do not contradict them.
  When guidance overlaps or conflicts, follow `1.01_merging_conflicting_rules`.
- Update or remove any existing guidance that the new rule replaces, rather than leaving both,
  explaining to the user what has been changed.

## Checklist

When creating or changing a rule:

1. Choose the category and the next free number, or keep the existing number.
2. Write the four-line header, then the content.
3. Check the content for accuracy and conflicts (see "Accuracy" and `1.01_merging_conflicting_rules`).
4. Add or update the matching entry in `docs/ai_rules/rule_index.json`.
5. When removing a rule, delete its file and its index entry, and update any rules that refer to it.
